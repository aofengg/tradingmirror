# 交易留痕三轮产品评测与优化报告

> 评测版本：MVP v0.2  
> 核心用户：有主业、用手机交易、缺少成熟交易体系、容易受情绪驱动的业余股票交易者。

## 1. 评测方法

本次三轮评测从以下角度对产品进行交叉检查：

- 目标用户匹配：是否适合碎片化、手机化、非专业交易场景；
- 输入成本：是否坚持零文字完成、最多 3 个核心输入；
- 行为设计：是否减少临场冲动，而不是训斥或教育用户；
- 数据语义：操作意图、实际成交、事后感受是否被正确区分；
- 复盘有效性：是否反映用户行为，避免事后市场结果替代决策评价；
- 情绪安全：是否允许懊悔和感受变化，不制造羞耻感；
- 留存与恢复：用户被工作中断后，是否能低成本继续；
- 可靠性：云数据库部分更新失败时，是否会造成重复提交或记录丢失；
- 数据控制：用户是否能理解并管理自己的敏感交易记录；
- 视觉与可达性：小屏幕、单手操作、状态识别和触摸面积是否合理；
- 工程可维护性：是否与参考项目保持原生小程序、CommonJS 和分层架构一致。

本报告是专家启发式评估和工程检查，不代替真实用户可用性测试。

## 2. 第一轮：核心用户路径与交易事件语义

### 2.1 评测结论

第一版的三步记录已经满足「标的 → 操作 → 主要原因」的最小输入原则，但存在一个高优先级逻辑错误：

> 「操作前想一想」产生的只是交易意图，不能直接被计为真实交易。

原实现将操作前记录直接进入待回看和周复盘，会造成：

- 未真正下单的意图污染操作统计；
- 用户被追问一笔从未发生的交易感受；
- 周复盘中的临时操作比例失真；
- 产品对「事前拦截」和「事后记录」的边界不清晰。

同时，交易刚刚完成就立即进入「待回看」，用户很难产生真正的事后视角。

### 2.2 本轮优化

1. 新增 `execution_status`，明确区分：
   - `pending`：只记录了操作意图；
   - `executed`：用户确认已经执行；
   - `cancelled`：最后没有执行。
2. 事前意图不再直接进入交易复盘。
3. 首页对待确认意图只问一个问题：「后来真的操作了吗？」
4. 用户只需点击「已执行」或「没有」。
5. 只有 `executed` 事件才进入周复盘。
6. 已执行事件设置 18 小时回看缓冲，避免操作完成后立即追问感受。
7. 记录列表明确展示「待确认 / 已执行 / 未执行」。

### 2.3 本轮结果

- 输入负担：不变，事前记录仍为 3 个核心选择；
- 后续确认：仅 1 次点击；
- 数据可信度：操作意图与真实执行已分离；
- 复盘口径：只统计真实已执行操作。

## 3. 第二轮：情绪回看与行为洞察有效性

### 3.1 评测结论

用户的事后感受是产品核心数据，但第一版只在交易事件上显示「最新感受」，存在三个问题：

- 用户看不到自己从轻松、懊悔再到接受的变化过程；
- 同一交易的多次懊悔快照会被周复盘重复计数；
- 交易事件上的最新感受属于冗余数据，部分更新失败时可能与真实快照不一致。

如果直接统计所有感受快照，系统将错把「一个人对一笔交易反复纠结」表达为「多笔交易都令他懊悔」。

### 3.2 本轮优化

1. 回看页新增「感受变化」时间线。
2. 每次回看生成新快照，不覆盖过往感受。
3. 周复盘先按交易事件分组，每笔交易只使用最新感受统计满意或懊悔。
4. 新增 `changedFeelingCount`，识别感受发生反转的交易数量。
5. 回看统计只纳入当周已执行交易，避免其他周的回看污染当周口径。
6. 记录列表在读取时用感受快照回填最新状态，减少对交易事件冗余字段的依赖。

### 3.3 本轮结果

- 用户可以看到感受反转，不再追求虚假的「最终判定」；
- 周复盘的懊悔数从「快照数」改为「最新感受为懊悔的交易数」；
- 同一交易多次回看不会夸大问题；
- 产品可以识别「对股价变化高度敏感，感受频繁反转」这类真正的行为特征。

## 4. 第三轮：留存、可靠性、数据控制与视觉完成度

### 4.1 评测结论

目标用户最常见的不是「不会填」，而是「填到一半被工作打断」。原实现中，页面被关闭后选择会丢失，会直接加重「我又没坚持」的挫败感。

同时发现：

- 感受快照已保存，但交易事件的冗余状态更新失败时，客户端会报错并引导用户重复提交；
- 原底部导航使用文字符号，识别性和视觉完成度不足；
- 交易记录属于敏感个人数据，但用户缺少删除单条记录的明确入口；
- 单靠冗余的 `latest_feeling` 作为记录列表数据源，不足够可靠。

### 4.2 本轮优化

1. **本地草稿恢复**
   - 用户选完标的或操作后立即保存本地草稿；
   - 重新进入同类流程时自动回到上次步骤；
   - 页面明确提示「已恢复」，并提供「重新填写」；
   - 云端保存成功后立即清除草稿。
2. **感受保存可靠性**
   - `reflection_snapshots` 是事后感受的真实数据源；
   - 快照已保存时，后续冗余字段同步失败不再诱导用户重复提交；
   - 首页待回看和记录列表直接对照感受快照。
3. **数据控制**
   - 每条记录提供轻量管理入口；
   - 删除前二次确认；
   - 删除交易记录时同时软删除关联感受快照。
4. **视觉与可达性**
   - 底部导航的临时文字符号替换为 4 组统一线性 SVG 图标；
   - 选中态同时使用颜色、背景和图标变化，不仅依赖单一颜色；
   - 保留高频操作的大点击区域，不在主流程增加文字输入。

### 4.3 本轮结果

- 工作中断不再意味着前面的选择全部作废；
- 用户不会因冗余状态更新失败而重复创建感受快照；
- 记录删除经过明确确认，避免意外丢失；
- 底部导航从工程占位状态进入可交付的统一品牌样式。

## 5. 三轮后的多角度评估

| 维度 | 当前结论 | 主要依据 |
|---|---|---|
| 目标用户匹配 | 高 | 事件触发、三步记录、零文字完成、支持中断恢复 |
| 输入负担 | 低 | 标的、操作、主要原因；懊悔时才条件展开第二问 |
| 行为产品差异化 | 高 | 不提供行情、选股和买卖建议，首页只服务记录与回看 |
| 交易数据完整度 | 有意克制 | 不强制价格、仓位、盈亏，优先持续性而非全量交易记账 |
| 复盘口径 | 可解释 | 区分计划性、执行状态和主观感受，不裁定投资对错 |
| 情绪安全 | 高 | 不打分、不连续打卡、不使用训斥文案，保留感受变化 |
| 数据可靠性 | 中高 | 真实快照与冗余状态分离；仍依赖云数据库连接 |
| 隐私与控制 | 中高 | 仅创建者可读写、单条删除、不采集券商账户和仓位 |
| 视觉完成度 | 中高 | 统一青绿品牌、大点击区、可识别图标和低压力信息层级 |
| 工程可维护性 | 高 | 原生小程序、CommonJS、Service/Repository 分层、纯函数行为统计测试 |

## 7. 真实用户测试建议

建议招募 5—8 名符合目标画像的业余交易者，在不讲解功能的情况下完成：

1. 记录一笔刚刚完成的清仓；
2. 在第 2 步退出小程序，重新打开并继续；
3. 记录一个事前意图，然后标记最终没有执行；
4. 对一笔记录标记「懊悔·卖早了」；
5. 修改这笔交易的当前感受，并找到感受历史；
6. 阅读周复盘并选择下周唯一提醒。

建议验收指标：

- 首次操作记录的中位完成时间不超过 20 秒；
- 不经解释的核心任务完成率不低于 80%；
- 用户能清楚说出「这不是荐股工具」；
- 用户能区分「按计划」和「现在是否懊悔」；
- 至少 4 人认为记录负担明显低于自己用过的交易日志。
